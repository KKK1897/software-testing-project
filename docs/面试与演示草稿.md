# 面试讲解与10分钟演示草稿

只讲已有证据，不把上游ERP写成自己开发，不声称线上运行、压力容量或远程CI通过。

## 项目讲解

我以jshERP v3.5固定提交搭建独立进销存测试环境，重点验证采购、调拨、销售后的库存和单据一致性。先查代码和系统配置，发现默认关闭强制审核、允许负库存，因此保存就影响库存，缺货拒绝需要单独关闭负库存策略后测试。

主链路创建独立商品，A采购100，A调拨30到B，B销售10。每一步都通过库存API验证，最后A70、B20、合计90，并按单号核对三张单据，不只验证接口200。页面测试另真实完成采购100和销售10后库存90，不能把它讲成页面调拨验证。

### 案例一：失败不一定意味着业务写入失败

测试运行中保存返回成功，下一次查询却收到loginOut。我查服务日志和LogService代码，发现同用户/IP/模块同秒重复操作会清除会话，而业务写入可能已经发生。普通回归因此使用明确写入节奏，并禁止清理任务和测试同时运行；没有用无限重试掩盖问题。这一行为作为待澄清规则保留，不能仅凭不喜欢该设计就计为产品缺陷。

### 案例二：通过多种查询排除脚本误判

回滚测试要证明非法单据没有落库。最初按不存在单号查详情得到业务500，导致6条用例失败。定位发现服务对空列表直接取第一个元素。我将“查询接口本身异常”单独提为DEF-001，同时通过列表零行和库存不变继续验证回滚。隔离补丁只补空列表判断，同一失败用例在补丁端口通过，原始端口保留失败。

### 案例三：页面权限与后端权限分别验证

通过管理接口创建只有仓库查询菜单、无新增按钮的只读账号。浏览器确认新增按钮不存在，但用该账号Token调用新增接口业务成功，管理员列表查询确认多了一条仓库，形成DEF-002。影响范围只写已证明的仓库新增接口，未声称所有模块都越权。此问题未修复，质量报告必须保留不通过结论。

### 常见追问

- 为什么不大量写SQL？业务系统应主要通过接口/页面验收。仅用SELECT DATABASE(), @@datadir核对清理环境，日志中的SQL用于定位。
- 如何数据隔离？每个业务用例唯一QA标识，记录商品与仓库ID的manifest，清理前校验本机数据库、目录、ID和名称，再逆序调用业务删除接口。
- 怎么判断自动化失败？区分产品、脚本、数据、环境和规则不清。仓库名22字符超数据库20字符是测试数据问题；空列表异常有代码和补丁证据。
- 性能能支持多少人？本项目只做1/3/5用户小负载，线程数不等于每秒请求；结果仅适用该机器和数据量，不能承诺线上容量。

## 约10分钟演示路线

全部命令在项目根目录执行；先确认没有其他写入测试或清理任务。

|时间|动作|展示证据|
|---|---|---|
|0:00—1:00|运行`.venv/Scripts/python.exe scripts/start_local.py`，打开本机3000页面|登录、会话与商品查询健康验收|
|1:00—2:00|执行`core_scenario.py`|新QA商品、A70/B20/总90及三张单据JSON|
|2:00—4:00|执行`.venv/Scripts/python.exe -m pytest tests/test_api.py -k "stock_chain or invalid_credentials or duplicate_number_no_extra_stock" -p no:cacheprovider`|现场选定高价值回归，完整回归结果展示现有报告|
|4:00—6:00|执行`.venv/Scripts/python.exe -m pytest tests/test_ui.py -k purchase_and_sale -p no:cacheprovider`|真实Chromium操作、截图/trace、采购销售库存证据|
|6:00—7:00|打开基线Allure报告|区分passed/failed/broken/skipped；失败不隐藏|
|7:00—8:30|展示DEF-001原始请求、服务空列表代码、最小patch与patch-junit.xml|从问题到定位到回归的完整证据|
|8:30—9:30|展示只读UI截图和readonly-create-evidence.json|页面隐藏、后端数据写入的对照|
|9:30—10:00|展示性能summary和遗留清单|说明负载模型、数据规模、未修复缺陷及CI实际状态|

演示前确认已有编译产物和浏览器依赖，首次下载/构建不计入10分钟。完整回归需要数分钟，不承诺在演示中重新执行全部用例。使用现存Allure/JUnit/截图对照历史证据，不将尚未执行的远程CI当成果。
